# Webapp changes needed (triggered by Customer App development)

Since the Customer App shares the `chillmama-Webapp` database and backend, some Customer App work will require changes on the webapp side. Track those here as they come up, so they don't get lost or forgotten when work eventually happens in that repo (on a different machine/session). When Claude Code (in this repo) identifies a needed webapp-side change, it should add an entry here with enough context to hand off cleanly — assume whoever picks it up won't have this conversation's context.

**Workflow reminder**: this file lives in the customer-app repo (where the need is discovered), but the actual work happens in the `chillmama-Webapp` repo. When you're ready to act on an item, copy it into that repo's own `CLAUDE.md` or open a tracked issue there, then mark it "In progress" here.

## Needed

- **Real `RESEND_API_KEY` for OTP email delivery** — the new email-OTP verification flow (2026-08-17, see Done section) sends via the already-wired Resend integration, but the local `.env` still has the `re_placeholder` key from `.env.example`, so no real email is ever delivered right now — verified via `grep`, not by reading the actual key value. Needs a real Resend API key + a verified sending domain before this works outside dev. Until then, registration is only testable using the dev-only `debugOtp` field (see below).
- **Schedule the pending-registration cleanup cron** — `POST /api/cron/cleanup-pending-registrations` (2026-08-17) exists and is gated by the already-present `CRON_SECRET` env var, but nothing calls it yet — no Vercel Cron config (`vercel.json` has no `crons` block) and no external scheduler. The 1-hour OTP expiry is already enforced at verify/resend time regardless (expired rows are rejected and deleted lazily on next access), so this is DB hygiene, not a correctness gap — but stale `pending_customer_registrations` rows will accumulate until it's scheduled.
- **Remove/gate the `debugOtp` dev escape hatch before any production-adjacent deploy** — `src/lib/auth/otp.ts`'s `debugOtpField()` includes the raw OTP in the `/register` and `/resend-otp` API responses whenever `NODE_ENV !== 'production'`. This was added so registration is testable locally without a real Resend key (see above) — it should never fire in production since NODE_ENV is 'production' there, but worth a deliberate look before any staging environment is exposed beyond localhost, since "not production" isn't the same guarantee as "not reachable."
- **Social login (Google/Apple/Facebook) for `/api/mobile/auth/*`** — Customer App's Login/Register screens now show "Continue with Google/Apple/Facebook" buttons (2026-08-16), but they're UI stubs (tap shows a "coming soon" alert) — there's no backend support yet. Needed to make these real:
  - A mobile OAuth token-exchange endpoint (e.g. `POST /api/mobile/auth/oauth`) that takes a provider + provider token (from `expo-auth-session` / `expo-apple-authentication` / the Facebook SDK on the client) and returns the same `{ accessToken, refreshToken, customer }` shape the existing `/register` and `/login` endpoints return — creating a `Customer` record on first sign-in if one doesn't exist for that provider identity.
  - Provider app credentials, which only the user/org can create: a Google OAuth client (Web + iOS + Android client IDs), an Apple Services ID + Sign in with Apple key, and a Facebook App ID — none of these exist yet as far as this repo's `.env.example` shows.
  - Apple's App Store review guidelines require "Sign in with Apple" to be offered if any other third-party social login is offered — since Google/Facebook are planned, Apple needs to ship alongside them, not be deferred.
- **Verify/add `language` field on Helper profiles** — needed for the Customer App's recommendation filtering (e.g. "prefer Cantonese-speaking helper"). Check the current Prisma schema — if it doesn't exist, this is a schema migration on the webapp side first.
- **Remaining `/api/mobile/` work** — reviews, search/filter by area/language, and reschedule/cancel for existing bookings (see `OPEN-QUESTIONS.md`). Bookings create/list-upcoming and helper recommend/detail/previous are shipped (2026-08-17, see Done).

## Done

- **`/api/mobile/auth/*` endpoints** — register, login, refresh, logout are shipped (JWT-based, `Customer` table only — `role` is hardcoded to `CUSTOMER` server-side, no Helper path). Wired up in the Customer App's Login/Register screens (2026-08-16). Contract: `POST /register` `{ name, email, password }`, `POST /login` `{ email, password }`, both return `{ accessToken, refreshToken, customer }` under `data`. Refresh-token rotation (`/refresh`) not yet consumed by the app — access token isn't auto-refreshed on expiry yet, that's a follow-up.
- **Email-OTP registration verification (2026-08-17)** — registration is now two steps. `POST /register` (`{ name, email, password }`) no longer creates a `User` immediately — it creates/refreshes a `PendingCustomerRegistration` row (new Prisma model, migration `20260817051955_add_pending_customer_registration`), emails a 6-digit code via the existing `sendOtpEmail` (`src/lib/email/index.ts`), and returns `{ email, otpExpiresAt }` (no tokens). `POST /verify-otp` (`{ email, otp }`) checks the code (bcrypt-hashed, 5-attempt lockout, 1-hour expiry via `src/lib/auth/otp.ts`), and only then creates the real `User` (`emailVerified` set) + `Customer` row and returns the usual `{ accessToken, refreshToken, customer }`. `POST /resend-otp` (`{ email }`, 60s cooldown) re-sends without needing the full form again. `/login` now rejects any `User` with `emailVerified` unset (defensive — not reachable via the app's own flow today, since unverified registrations never create a `User`, but guards e.g. accounts created directly via the admin panel). Mobile side: new `screens/OtpScreen.tsx`, wired into `RegisterScreen` → `Otp` → `Chat`. Verified end-to-end (happy path, wrong code, 5-attempt lockout, resend cooldown, expired-code rejection, unverified-login rejection) against the local dev DB.
- **Password complexity validation (2026-08-17)** — `mobileRegisterSchema`'s password field (`src/lib/validators/index.ts`) now requires 8-16 characters with at least one uppercase letter, one lowercase letter, one number, and one special character from an explicit allowlist (`!@#$%^&*()-_=+`) — any other character (quotes, backslash, angle brackets, whitespace, unicode, etc.) is rejected outright, not just "not required." Exported as `mobilePasswordSchema` for reuse. `/login`'s password field is unchanged (`min(1)`) — login should never re-validate complexity against existing accounts. Mirrored client-side in the Customer App (`services/passwordValidation.ts`, matching rules/messages/order) so weak passwords are rejected before hitting the network, plus an inline requirements hint under the password field on `RegisterScreen`. Verified: length bounds, each missing character class, a disallowed character, and a valid password, both via curl against the real endpoint and end-to-end through the app UI.
- **Helper swipe-card recommendations, backend + mobile (2026-08-17)**:
  - **Seed data**: `prisma/seed.ts` now creates 6 sample Helpers (with a `User` + one `ACTIVE` `Service` each) spanning childcare/cleaning/cooking/pet-care/tutoring/errands, reusing existing seeded categories/areas. Photos are `pravatar.cc` placeholder headshots — not real people, not R2-hosted. Idempotent (upserts by email/userId/a stable service id), safe to re-run.
  - **`GET /api/mobile/helpers/recommended`** — auth-required (mobile Bearer token via `verifyAccessToken`), returns visible/approved helpers with an active service, ordered by rating: `{ id, name, photoUrl, rating, jobsCompleted, fee, serviceTitle }`. Not filtered by anything the AI chat would eventually parse (service type/date/language/etc.) — that pipeline doesn't exist yet, so this just returns the whole visible pool.
  - **`GET /api/mobile/helpers/:id`** — same auth, adds `bio`, `completionRate`, `serviceDescription`, `areaName`. 404s for a missing/unapproved/invisible helper or one with no active service.
  - Mobile: `components/HelperSwipeDeck.tsx` — hand-rolled with `react-native-gesture-handler` + `react-native-reanimated` (not `react-native-deck-swiper`, which has no dependency updates tracking this project's very new RN 0.86/React 19.2 combo, unlike gesture-handler/reanimated which `expo install` version-pins for the SDK). Swipe left/tap ✕ = next card (no persistence — see the still-open "swipe-left exclusion permanence" question in `OPEN-QUESTIONS.md`, deliberately not resolved here). Swipe right/tap 👁 = `screens/HelperDetailScreen.tsx`, nested in a new `navigation/ChatStack.tsx` under the Chat tab. Triggered from `ChatScreen` via a manual "Find helpers" button (the AI can't surface this on its own yet).
  - Required adding `babel.config.js` (didn't exist) + explicit `babel-preset-expo` devDependency — Reanimated needs its Babel plugin, and creating an explicit babel config broke implicit resolution of `babel-preset-expo`, which wasn't hoisted since it had never been a direct dependency before.
  - **Also fixed**: `services/tokenStorage.ts` now keeps an in-memory token cache alongside `SecureStore`. Previously, since `expo-secure-store` has no web implementation at all, a saved token was unrecoverable for the rest of the session on web (not just across reloads) — meaning every authenticated `/api/mobile/` call would silently drop its bearer token and 401, which is exactly what blocked this feature during testing. This is a real fix (a web build would want session-lived tokens even without persistent secure storage), not just a test workaround.
  - Verified end-to-end: curl against real seeded data (auth-required 401, list, detail, 404), and through the app UI (register → Chat → Find helpers → pass via button and via an actual drag gesture → view → detail screen renders → back button returns to the deck).
- **Scripted "Butler" booking routine + full booking backend (2026-08-17)** — the chat assistant now runs a full scripted flow on login: greeting → check upcoming bookings (ask which one if multiple, honest "can't reschedule/cancel yet" note on review) → if none, offer a new booking → category picker (real `Category` data) → offer to rebook a previous COMPLETED-booking helper for that category, or recommend new ones → swipe deck (tapping the photo now also opens detail, not just the eye button/swipe gesture) → detail screen's new "Book an appointment" button → 3 suggested time slots ("Show more times" pages the next 3) → creates the booking → confirms and returns to an idle/ready state. This is scripted/keyword-free (a real state machine reacting to button taps), not real NL understanding — see `OPEN-QUESTIONS.md`'s AI-backend-architecture question, still open. The prior free-text "clean/book/helper" keyword shortcut still works alongside it.
  - New endpoints (all auth-required, mobile Bearer token): `GET /api/mobile/categories`, `GET /api/mobile/bookings/upcoming`, `GET /api/mobile/helpers/previous?categoryId=` (COMPLETED bookings only, so "previous helper" means an actually-finished job, not just any past booking attempt), `GET /api/mobile/bookings/slots?serviceId=&offset=` (3-at-a-time conflict-avoidance slot suggestions — see the open question above for what this doesn't do yet), `POST /api/mobile/bookings` (creates with `status: CONFIRMED` directly — there's no Helper App yet for a helper-side accept/reject step, so "confirmed" here just means "the slot was free and got reserved," not "the helper acknowledged it," re-validates for conflicts at creation time too, 409s if the slot was taken in between). `/helpers/recommended` gained an optional `?categoryId=` filter; `/helpers/:id` now also returns `serviceId` (needed to start a booking). Refactored the auth-check boilerplate shared across all of these into `src/lib/auth/mobile-auth.ts`.
  - Mobile: new `contexts/ChatFlowContext.tsx` replaces the old local `useChatMessages` hook as the source of chat state — needed because `HelperDetailScreen`'s "Book an appointment" button has to inject messages back into the same conversation, so the flow state had to move up to a context shared across the whole `ChatStack` (wraps both `ChatScreen` and `HelperDetailScreen`). New presentational components: `QuickReplies`, `BookingListCard`, `SlotPicker`, `PreviousHelperCard`. `My Bookings` tab now shows real upcoming bookings (refetches on tab focus) instead of a static placeholder — leaving it stale once bookings actually existed would have been a glaring, self-created inconsistency.
  - **Caught and fixed during implementation** (not shipped broken): (1) several action handlers were reading current state via a `setMessages(current => { ...side effects...})` peek, which is unsafe — React can invoke updater callbacks more than once (notably Strict Mode's dev-time double-invocation), which could have double-fired API calls or, worse, created duplicate bookings; refactored to read from a ref mirror of state instead, with side effects only ever running in plain callbacks. (2) After declining to review an existing upcoming booking, the assistant incorrectly said "you don't have any upcoming bookings" (the same "ask about a new service" prompt is used whether there were zero bookings or the customer just chose not to review them) — fixed by threading which case it is into the prompt wording.
  - Verified end-to-end for every branch: zero bookings, one booking (singular wording), multiple bookings (plural wording + list), reviewing a selected booking, category picker with real categories, no-previous-helper (falls straight through to recommendations), has-previous-helper (rebook offer + card), full slot-picker including pagination and a real booking creation, and the Bookings tab reflecting a just-created booking. All via curl against seeded/manually-inserted data and through the full app UI, zero console errors in the final runs.
