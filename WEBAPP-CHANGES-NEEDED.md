# Webapp changes needed (triggered by Customer App development)

Since the Customer App shares the `chillmama-Webapp` database and backend, some Customer App work will require changes on the webapp side. Track those here as they come up, so they don't get lost or forgotten when work eventually happens in that repo (on a different machine/session). When Claude Code (in this repo) identifies a needed webapp-side change, it should add an entry here with enough context to hand off cleanly — assume whoever picks it up won't have this conversation's context.

**Workflow reminder**: this file lives in the customer-app repo (where the need is discovered), but the actual work happens in the `chillmama-Webapp` repo. When you're ready to act on an item, copy it into that repo's own `CLAUDE.md` or open a tracked issue there, then mark it "In progress" here.

## Needed

- **Real `RESEND_API_KEY` for OTP email delivery** — the new email-OTP verification flow (2026-08-17, see Done section) sends via the already-wired Resend integration, but the local `.env` still has the `re_placeholder` key from `.env.example`, so no real email is ever delivered right now — verified via `grep`, not by reading the actual key value. Needs a real Resend API key + a verified sending domain before this works outside dev. Until then, registration is only testable using the dev-only `debugOtp` field (see below).
- **Schedule the pending-registration cleanup cron** — `POST /api/cron/cleanup-pending-registrations` (2026-08-17) exists and is gated by the already-present `CRON_SECRET` env var, but nothing calls it yet — no Vercel Cron config (`vercel.json` has no `crons` block) and no external scheduler. The 1-hour OTP expiry is already enforced at verify/resend time regardless (expired rows are rejected and deleted lazily on next access), so this is DB hygiene, not a correctness gap — but stale `pending_customer_registrations` rows will accumulate until it's scheduled.
- **Remove/gate the `debugOtp` dev escape hatch before any production-adjacent deploy** — `src/lib/auth/otp.ts`'s `debugOtpField()` includes the raw OTP in the `/register` and `/resend-otp` API responses whenever `NODE_ENV !== 'production'`. This was added so registration is testable locally without a real Resend key (see above) — it should never fire in production since NODE_ENV is 'production' there, but worth a deliberate look before any staging environment is exposed beyond localhost, since "not production" isn't the same guarantee as "not reachable."
- **Social login (Google/Apple/Facebook) for `/api/mobile/auth/*`** — Customer App's Login/Register screens now show "Continue with Google/Apple/Facebook" buttons (2026-08-16), but they're UI stubs (tap shows a "coming soon" alert) — there's no backend support yet. Needed to make these real:
  - A mobile OAuth token-exchange endpoint (e.g. `POST /api/mobile/auth/oauth`) that takes a provider + provider token (from `expo-auth-session` / `expo-apple-authentication` / the Facebook SDK on the client) and returns the same `{ accessToken, refreshToken, customer }` shape the existing `/register` and `/login` endpoints return — creating a `Customer` record on first sign-in if one doesn't exist for that provider identity.
  - Provider app credentials, which only the user/org can create: a Google OAuth client (Web + iOS + Android client IDs), an Apple Services ID + Sign in with Apple key, and a Facebook App ID — none of these exist yet as far as this repo's `.env.example` shows.
  - Apple's App Store review guidelines require "Sign in with Apple" to be offered if any other third-party social login is offered — since Google/Facebook are planned, Apple needs to ship alongside them, not be deferred.
- **Verify/add `language` field on Helper profiles** — needed for the Customer App's recommendation filtering (e.g. "prefer Cantonese-speaking helper"). Check the current Prisma schema — if it doesn't exist, this is a schema migration on the webapp side first.

## Done

- **`/api/mobile/auth/*` endpoints** — register, login, refresh, logout are shipped (JWT-based, `Customer` table only — `role` is hardcoded to `CUSTOMER` server-side, no Helper path). Wired up in the Customer App's Login/Register screens (2026-08-16). Contract: `POST /register` `{ name, email, password }`, `POST /login` `{ email, password }`, both return `{ accessToken, refreshToken, customer }` under `data`. Refresh-token rotation (`/refresh`) not yet consumed by the app — access token isn't auto-refreshed on expiry yet, that's a follow-up.
- **Email-OTP registration verification (2026-08-17)** — registration is now two steps. `POST /register` (`{ name, email, password }`) no longer creates a `User` immediately — it creates/refreshes a `PendingCustomerRegistration` row (new Prisma model, migration `20260817051955_add_pending_customer_registration`), emails a 6-digit code via the existing `sendOtpEmail` (`src/lib/email/index.ts`), and returns `{ email, otpExpiresAt }` (no tokens). `POST /verify-otp` (`{ email, otp }`) checks the code (bcrypt-hashed, 5-attempt lockout, 1-hour expiry via `src/lib/auth/otp.ts`), and only then creates the real `User` (`emailVerified` set) + `Customer` row and returns the usual `{ accessToken, refreshToken, customer }`. `POST /resend-otp` (`{ email }`, 60s cooldown) re-sends without needing the full form again. `/login` now rejects any `User` with `emailVerified` unset (defensive — not reachable via the app's own flow today, since unverified registrations never create a `User`, but guards e.g. accounts created directly via the admin panel). Mobile side: new `screens/OtpScreen.tsx`, wired into `RegisterScreen` → `Otp` → `Chat`. Verified end-to-end (happy path, wrong code, 5-attempt lockout, resend cooldown, expired-code rejection, unverified-login rejection) against the local dev DB.
- **Password complexity validation (2026-08-17)** — `mobileRegisterSchema`'s password field (`src/lib/validators/index.ts`) now requires 8-16 characters with at least one uppercase letter, one lowercase letter, one number, and one special character from an explicit allowlist (`!@#$%^&*()-_=+`) — any other character (quotes, backslash, angle brackets, whitespace, unicode, etc.) is rejected outright, not just "not required." Exported as `mobilePasswordSchema` for reuse. `/login`'s password field is unchanged (`min(1)`) — login should never re-validate complexity against existing accounts. Mirrored client-side in the Customer App (`services/passwordValidation.ts`, matching rules/messages/order) so weak passwords are rejected before hitting the network, plus an inline requirements hint under the password field on `RegisterScreen`. Verified: length bounds, each missing character class, a disallowed character, and a valid password, both via curl against the real endpoint and end-to-end through the app UI.
